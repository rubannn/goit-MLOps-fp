# ADR: Deployment-стратегія — Canary (90/10)

## Контекст

Проєкт — MLOps-платформа для рекомендаційної системи фільмів (MovieLens, Matrix Factorization). Потрібно обрати одну з трьох стратегій деплою нової версії моделі: Canary, Blue-Green або A/B testing (`plan.md`, Блок B3).

## Рішення

**Canary, 90/10**, реалізований на чистому Kubernetes (без Ingress-контролера чи service mesh):

- `production` namespace містить 2 Deployment за **одним** Service, селектор якого навмисно **не включає** лейбл `track` — лише спільний `app: movielens-inference`:
  - `movielens-inference-stable` — 9 реплік, завантажує модель зі стадії **Production** MLflow Registry.
  - `movielens-inference-canary` — 1 репліка, завантажує модель зі стадії **Staging** (наступний кандидат).
- Оскільки Service балансує трафік по всіх подах з відповідним лейблом, співвідношення реплік (9:1) визначає фактичний розподіл трафіку — без додаткової інфраструктури.
- Promotion (`experiments/promote_model.py`) і rollback (`experiments/rollback_model.py`) — окремі, явні дії; жодна нова версія не потрапляє в Production автоматично після тренування.

Перевірено практично: 259 запитів через ClusterIP Service → 87.6% stable / 12.4% canary — близько до цільових 90/10 (відхилення — статистичний шум від random-балансингу kube-proxy на малій кількості подів, не системна помилка).

## Чому саме Canary, а не Blue-Green чи A/B

| Критерій | Canary (обрано) | Blue-Green | A/B testing |
|---|---|---|---|
| Домен | Рекомендація фільму — **low-stakes**: помилка нової моделі означає гіршу рекомендацію, не шкоду користувачу | Кращий вибір для **high-stakes** доменів (напр. медичні/фінансові рішення), де жоден користувач не повинен бачити неперевірену модель | Потребує довшого, статистично значущого спостереження за конверсією — оверкілл для навчального проєкту з малим трафіком |
| Індустрійна відповідність | Саме так рекомендаційні системи розкатуються в Netflix/YouTube/Spotify — новий алгоритм отримує % живого трафіку, метрики порівнюються в реальному часі | Типово для критичних сервісів або релізів "усе-або-нічого" | Типово для маркетингових/UX-експериментів з тривалим циклом |
| Складність реалізації | Мінімальна на "голому" Kubernetes — 2 Deployment + 1 Service, без Ingress-контролера чи service mesh | Вимагає повного дублювання оточення і миттєвого перемикання (Service selector swap) — так само просто, але дає **менше** сигналу (жоден реальний запит не бачить нову модель до switch) | Вимагає явного tracking експериментів (variant assignment, статистичні тести) — не покривається базовим Kubernetes Service |
| Rollback | Просто зменшити/прибрати canary-репліки або redeploy Staging-стадії | Миттєве перемикання назад на Blue | Завершення експерименту, вибір переможця |

Blue-Green був би сильнішим вибором, якби датасет був "high-stakes" (наприклад, розглядався варіант з Mushroom dataset — класифікація "їстівний/отруйний гриб", де жоден реальний користувач не повинен отримати непровалідовану модель навіть на 10% запитів). Для MovieLens ця обережність не потрібна — Canary дає більше практичної цінності (реальні метрики на живому трафіку) за ту саму складність реалізації.

## Trade-off-и

- **Точність розподілу трафіку (9:1 через replica count) — не гарантована на 100%.** kube-proxy балансує "приблизно рівномірно" між ендпоінтами, а не строго round-robin per-request у всіх режимах (iptables-режим — псевдо-випадковий вибір). На малій кількості подів (10) це дає помітні статистичні відхилення (87.6/12.4% замість точних 90/10) — прийнятно для демонстрації, але не підійшло б для точного A/B-експерименту, де потрібна детермінована атрибуція трафіку.
- **Немає автоматичного відкату при деградації canary** (Блок G2 — бонусний, не реалізовано). Зараз рішення "canary погана — відкотити" ухвалює людина, дивлячись на Grafana-дашборд.
- **Rate limiting — per-под**, отже сумарна пропускна здатність canary (1 репліка) штучно нижча за stable (9 реплік) — можливий побічний ефект: canary частіше впирається в rate limit при рівномірному навантаженні. Не є проблемою для навчального навантаження, але вартий уваги при реальному трафіку.
- **Один Docker-образ для всіх треків** (staging/stable/canary) — відрізняється лише `MODEL_STAGE` env var. Спрощує CI/CD (один build), але означає, що будь-яка зміна коду inference-сервісу одночасно зачіпає всі три деплойменти при оновленні образу — немає ізольованого "canary коду", лише "canary моделі".

## Що зроблено б інакше за наявності більше часу

1. **Service mesh (Istio/Linkerd) або Ingress з traffic-splitting** замість replica-count-ratio — дає точний, детермінований відсоток трафіку (напр. точно 10.0%, а не приблизно), і можливість canary за іншими вимірами (header-based routing для internal testing перед публічним canary).
2. **Redis-backed rate limiter** — прибирає per-под ліміт на користь справжнього кластерного rate limiting.
3. **External Secrets Operator / Vault / Sealed Secrets** замість ручного `kubectl create secret` під час bootstrap — поточне рішення (Kubernetes Secret + `existingSecret` у Helm-values) вже прибирає креденшели з git, але не дає ротації, аудиту доступу чи інтеграції з centralized secret-manager. Прийнятний наступний крок, не критичний для навчального проєкту з коротким життєвим циклом інфраструктури.
4. **Автоматичний rollback у Canary** (Блок G2) — Prometheus alert на зростання error rate/latency canary-подів запускає автоматичний `kubectl scale deployment/movielens-inference-canary --replicas=0`, без очікування ручного втручання.
5. **Multi-armed bandit замість фіксованого 90/10** — динамічне збільшення частки canary в міру накопичення довіри до нової версії (замість ручного рішення "тепер promote to Production").
